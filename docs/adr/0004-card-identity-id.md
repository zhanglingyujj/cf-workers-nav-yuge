# 0004: 引入卡片 id 作为卡片身份

日期：2026-09-05
状态：已接受（取代 0003）

## 背景

0003 暂缓引入 id 后，落地改进方案（阶段 0/1：按引用定位 + DOM 查找限定分组）只能收窄风险，无法消除"同 URL 双卡命中错误目标"的结构性问题：`patchCategory` 的 DOM 对账、拖拽的 `readLinksFromDOM`、编辑/删除入口全部依赖 url 唯一性。本次作为前置基建直接落地完整方案，为卡片级历史/统计等需要稳定身份的功能铺路。

## 决策

**为每张卡片引入 `id`（`crypto.randomUUID()`，惰性补齐），id 是定位键，url 降为普通业务属性。**

1. **惰性迁移，零停机**：读取时补齐——后端 `normalizeCategories`（getLinks 出口）与前端 `setCategories` 为缺失 id 的 link 生成 id，随下一次 commit 落库；无迁移脚本。
2. **id 只增不改、不换身份**：`updateLink` 替换对象时继承旧 id；`addLink`/导入书签为新卡生成 id。
3. **DOM 层双属性并存**：卡片元素同时携带 `data-card-id`（定位、对账键）与 `data-url`（打开链接、数字键快捷跳转等纯消费 url 的场景不变）。
4. **导出兼容**：本站原生格式导出携带 id（往返不换身份）；Sun-Panel 格式不含 id（本就单向降级，多余字段会被忽略）；导入旧格式（无 id）由 normalize 补齐。
5. **mutator 按引用定位，id 兜底**：`updateLink(oldLink, newLink)` / `removeLink(linkRef)` 按对象引用定位，弹窗打开期间 state 被整体替换导致引用陈旧时按 id 兜底命中。

## 后果

- DOM 对账键切换当帧，惰性迁移首帧旧卡可能被判定为"新增+删除"导致整卡重建（视觉上闪一下，无数据损坏）。
- 书签导入的组内去重仍按 url（业务语义：同站点视为重复），与卡片身份无关。
- 0003 的重启条件由本决策提前兑现，url 身份相关的遗留查找全部清除。
